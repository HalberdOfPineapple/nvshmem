Code walkthrough

GPU Data Movement Paths

Every way NVSHMEM can move bytes from one GPU's memory to another's: which hardware does the copying, who starts it, which source function picks it, how the bytes travel through registers, L1, shared memory, L2 and HBM on both GPUs, and when TMA is the right choice.

NVSHMEM 3.9.0.dev0 branch devel @ 7bb2e99 paths relative to repo root companion to tma-smem-walkthrough.html
Overview A

Short answer

TMA is not the default for GPU-to-GPU copies

A device-side put or get to a peer GPU reachable over NVLink is done by ordinary thread loads and stores unless all of these hold: NVSHMEM_TMA_POLICY=ENABLE (or FORCE), the GPU is sm_90 or newer, the calling block has lent shared memory with nvshmemx_give_smem, and both addresses and the byte count are multiples of 16. If any check fails, the same call silently falls back to thread load/store (nvshmemii_put_nbi, src/include/non_abi/device/common/nvshmemi_common_device.cuh:1444-1472).

TMA is worth enabling when the data is already in shared memory (for example the output tile of a fused GEMM), or when only a few threads issue the transfer and you want the other threads free for computation. It does nothing for peers reached over the network, and it costs shared memory (64 KiB per block recommended). Section E has the full reasoning.

Besides thread load/store and TMA, NVSHMEM has five other ways to move data: NVLink multicast stores through the NVSwitch, the GPU's copy engines (started from the host with cudaMemcpyAsync), a CPU proxy thread that drives the InfiniBand card, IBGDA (the GPU drives the InfiniBand card itself), and "logical endpoint" handles on the newest CUDA. The map below shows all seven.

Overview C

Terms used on this page

PE
Processing element: one process of the job, owning one GPU.
P2P / NVLink-reachable
The peer GPU's memory is mapped into this GPU's address space, so a normal pointer to it works. NVSHMEM records this as a non-null entry in peer_heap_base_p2p[pe]. On Beta that is the other 3 GPUs of the node, and, when multi-node NVLink works, all 72 GPUs of the rack.
SM
Streaming multiprocessor: one of the ~150 compute units of a GPU. A thread block runs on one SM.
ld / st
Load and store instructions executed by threads. A store to a peer address travels over NVLink.
TMA
Tensor Memory Accelerator: a copy unit inside each SM (sm_90 Hopper, sm_100 Blackwell) that copies between shared memory and global memory after one thread starts it.
copy engine (CE)
A DMA unit on the GPU, separate from the SMs, used by cudaMemcpy*. It uses no SM time but can only be started from the host through a CUDA stream.
NVLS / multimem
NVLink SHARP: the NVSwitch can copy one store to many GPUs (multimem.st) or add up values from many GPUs on a load (multimem.ld_reduce). Addresses must come from a multicast object.
NIC / HCA
Network interface card (InfiniBand "host channel adapter"). It can read and write GPU memory directly (GPUDirect RDMA).
RDMA, WQE, doorbell
Remote direct memory access: the NIC copies memory to a remote node without that node's CPU. A work-queue entry (WQE) describes one copy; writing the "doorbell" register tells the NIC to start.
proxy thread
A CPU thread NVSHMEM starts at init. It reads requests that GPU kernels write into a ring buffer and posts them to the NIC.
IBRC
InfiniBand Reliable Connection transport: NVSHMEM's host-driven IB transport (src/modules/transport/ibrc), used by the proxy.
IBGDA
InfiniBand GPUDirect Async: GPU threads build WQEs and ring the doorbell themselves, with no CPU in the loop.
scope (thread / warp / block)
How many threads call the API together: nvshmem_putmem is one thread, nvshmemx_putmem_warp 32 threads, nvshmemx_putmem_block the whole block.
nbi
Non-blocking-initiation: the call may return before the data arrives; nvshmem_quiet waits for completion.
mbarrier
A hardware barrier object in shared memory. TMA loads signal it when their bytes have landed.
Overview C2

The memory parts every path goes through

All the traffic diagrams below use the same drawing of a GPU. The rules that decide which parts a byte visits are few:

PartRule that matters for communication
registersPrivate to one thread. Path 1 and 3 move every byte through them; TMA, copy engine and NIC paths never do.
L1 cacheOne per SM, not coherent with other SMs or GPUs. Global stores are write-through (they go on to L2). A thread polling a flag that someone else writes must bypass L1 (volatile, ld.acquire, ld.relaxed.sys).
shared memorySame SRAM as L1 (up to 228 KiB of the per-SM array can be shared memory on Hopper/Blackwell). Written by threads through the generic proxy and by TMA through the async proxy; fence.proxy.async orders the two. Other SMs, other GPUs and NICs cannot address it, which is why a shared-memory source cannot go to the network.
TMA unitMoves bytes between shared memory and the crossbar. Its loads go L2 → shared memory without allocating in L1.
crossbarRoutes each request by physical address: to a local L2 slice, or out through an NVLink port (peer memory) or PCIe / C2C (host memory, NIC registers).
L2 cacheShared by the whole GPU and the point of coherence for that GPU's HBM: every access to its HBM, from its own SMs, copy engines, peer GPUs over NVLink or NICs over PCIe, goes through it. A peer's write is therefore visible to all of the owner's SMs as soon as it reaches the owner's L2.
HBMWhere the symmetric heap lives. L2 writes lines back to it later; no communication path writes HBM without passing its L2.

These rules come from NVIDIA's public architecture and PTX documentation, not from the NVSHMEM source. The NVSHMEM behaviour on each diagram (which instruction, which thread, which fence) is traced from the source with file and line.

PATH 1

Thread load/store over NVLink

nvshmemi_common_device.cuh:327-438

The default. NVSHMEM converts your symmetric address to the peer's mapped address (peer_base + (dest − heap_base)) and then every thread of the calling group copies a slice with plain C++ assignments. The loop tries the widest access the alignment allows: 16-byte (int4), then 8, 4, 2 and 1 bytes for the tail.

Call chain
  1. nvshmemx_putmem_block(dest, src, n, pe)src/include/device/nvshmemx_defines.h
    1. nvshmemi_put<char, BLOCK>()common:1485
      1. nvshmemi_memcpy_threadgroup<BLOCK>(dest_actual, src, n)common:327Each of N threads moves every N-th 16-byte chunk.
  2. nvshmem_quiet()common:1185-1212On an NVLink-only job this is just __threadfence_system(): stores are already on their way, so it only has to order them.

Properties. Bandwidth grows with the number of threads issuing (each thread only keeps a few stores in flight), so a whole block or many blocks can fill NVLink, but one thread cannot. The source can be anywhere a thread can read: registers, shared memory, global memory. Works on every GPU generation and any alignment. Scalar puts (nvshmem_int_p) and SIGNAL_SET are single stores on this path (nvshmemi_p common:1421, nvshmemi_signal_op common:1519); signal adds are atomicAdd_system.

Doing it yourself. nvshmem_ptr(dest, pe) (src/include/device/nvshmem_defines.h:1404) returns the peer's mapped address, or NULL if not reachable. With that pointer you can write the peer's memory directly from your own code, which is how many fused kernels avoid the API's group synchronisations.

Memory traffic

A put with a source in local global memory. Every 16-byte chunk makes the round trip through one thread's registers.

#HopWhat happens
1A HBM → A L2The thread's ld.global.v4 misses in L1 and L2; L2 fetches the 32-byte sectors from HBM.
2A L2 → A L1Through the crossbar back to the SM. A default global load may keep a copy in L1.
3A L1 → registers16 bytes land in 4 registers of one thread.
4registers → crossbarst.global.v4 to the peer-mapped address. Stores are write-through, so L1 does not hold it. The address translates (TLB/MMU) to the peer, so the crossbar routes it to an NVLink port instead of a local L2 slice: A's L2 is not used for the destination.
5NVLink / NVSwitchThe write packet crosses the switch to GPU B.
6B L2 → B HBMIt is written into B's L2, the home of that address; L2 writes it back to HBM later. B's SMs are not involved.
7B consumer: B L2 → registersA thread on B waiting in nvshmem_wait_until polls through a volatile pointer (src/include/non_abi/device/wait/nvshmemi_wait_until_apis.cuh:37-48). Volatile loads skip L1, so they see the new value in L2. A plain cached load could keep reading a stale L1 line.

Variants. Source in shared memory: steps 1–3 are replaced by one ld.shared (shared memory → registers). Put-with-signal: after the data the issuing thread runs __threadfence_system() and then stores the signal, so the signal cannot reach B's L2 before the data (nvshmemii_put_signal, common:1561-1592).

#HopWhat happens
1registers → B L2ld.global to the peer-mapped address: a read request goes out through the crossbar and NVLink to B's L2.
2B HBM → B L2Only if the line is not already in B's L2.
3B L2 → A registersThe response crosses NVLink back to the requesting SM. The thread stalls on this round trip (roughly a microsecond, much longer than a local load), so gets need many threads in flight to reach bandwidth.
4registers → A L2st.global to the local destination, write-through past L1.
5A L2 → A HBMWritten back later.

Whether the requesting SM's L1 keeps a copy of peer data it loaded is not stated in NVSHMEM's source or NVIDIA's public documents. NVSHMEM does not rely on it: its waits use volatile loads.

PATH 2

TMA bulk copy over NVLink

pt-to-pt/tma_device.cuh, nvshmemi_common_device.cuh:444-1182

The TMA unit copies a contiguous run of bytes between the SM's shared memory and a global address. It cannot copy global→global directly, so NVSHMEM has four shapes, chosen by where the local operand lives:

Call chain, device put and get
  1. nvshmemi_tma_get_smem_registration()common:494-515Looks up this block's entry in the table filled by give_smem. Invalid if policy is DISABLE (default), arch < sm_90, or the block never registered.
  2. nvshmemi_memcpy_tma[_nbi]<SCOPE>()common:1164-1182Put dispatcher: __isShared(source) picks A, otherwise B.
    1. nvshmemi_memcpy_tma_shared_global<SCOPE, BLOCKING>()Atma_device.cuh:320-380Thread scope: the caller issues. Warp / block: one elect.sync leader issues the whole transfer as one instruction. The caller must first run fence.proxy.async.shared::cta (contract at tma_device.cuh:304-308).
    2. nvshmemi_memcpy_tma_global_global_single<SCOPE>()Bcommon:849-933Thread / warp scope. One tile (registered size − 1,136 bytes, ~63 KiB). Loop per chunk: load into tile, wait on mbarrier slot 0, store to peer, then wait_group.read 0 before reusing the tile. So load and store do not overlap.
    3. nvshmemi_memcpy_tma_global_global_block<BLOCKING>()Bcommon:963-1100Block scope, needs ≥ 64 threads. Double-buffered: two half-size tiles, ready_bar[2] / done_bar[2] mbarriers; thread 0 loads, thread 32 (warpSize) stores, so loads of tile i+1 overlap stores of tile i.
  3. nvshmemi_get<T, SCOPE>()common:1380-1413__isShared(dest) → nvshmemi_memcpy_tma_global_shared (C, common:777-830, mbarrier slot 4); otherwise nvshmemi_memcpy_tma_global_global with peer as source (D).

Completion: quiet vs flush

nvshmem_quiet

nvshmemi_tma_drain_if_registered(): commit_group + wait_group 0, i.e. wait until the TMA has finished writing, then __threadfence_system() (common:576-587, 1185-1212). Only waits for groups issued by the calling thread.

nvshmemx flush (source reuse)

wait_group.read 0 + proxy fence: wait only until the TMA has read the source, so you may overwrite it; the data may not have arrived yet (common:1224-1268). For path 1 flush is a no-op, because a store has already read its register.

The per-thread tracking is the trap noted in the tma-smem walkthrough: the block put's staged copies are issued by thread 32, and a later nvshmem_quiet() from thread 0 does not wait for them. Calling nvshmem_quiet() from every thread of the block (each drains its own groups) or using the blocking put avoids it (reading of the code, not verified by a run).

Memory traffic

The TMA unit sits beside the SM's L1/shared-memory SRAM and talks to the crossbar directly. Registers and L1 never hold the payload; that is the whole difference from path 1.

#HopWhat happens
1registers → shared memoryThreads write the payload with ordinary st.shared (the generic proxy). Then fence.proxy.async.shared::cta makes those writes visible to the TMA (async proxy).
2shared memory → TMAOne elected thread issues cp.async.bulk.global.shared::cta; the TMA reads the bytes straight out of shared memory.
3TMA → crossbarThe TMA emits write packets to the peer address; the crossbar sends them to NVLink. No L1, no A L2.
4NVLink / NVSwitchSame wire as path 1.
5B L2 → B HBMLands in B's L2 as before. Completion (wait_group 0 in quiet) means all writes have been performed.
#HopWhat happens
1A HBM → A L2The TMA's bulk load reads the source through A's L2.
2A L2 → TMAOver the crossbar to the TMA unit, not into L1.
3TMA → shared memoryThe TMA writes the tile and counts the bytes on an mbarrier (complete_tx); the issuing thread waits on it.
4shared memory → TMABulk store of the tile is issued (thread 32 in the block version, while thread 0 loads the next tile into the second buffer).
5TMA → NVLinkWrite packets to the peer.
6B L2 → B HBMAs shape A.

So shape B moves every byte through the SM's SRAM twice (in and out), compared with path 1's trip through registers. What it saves is instructions and threads, not memory traffic.

#HopWhat happens
1thread → TMAThe elected thread initialises an mbarrier in shared memory, sets the expected byte count (arrive_expect_tx) and issues cp.async.bulk.shared::cta.global with the peer address.
2TMA → B L2Read requests leave through the crossbar and NVLink.
3B HBM → B L2Only on an L2 miss.
4B L2 → A TMAThe response data returns over NVLink to A's TMA unit.
5TMA → shared memoryWritten into the destination and counted on the mbarrier.
6mbarrier → threadsWhen all bytes are counted the mbarrier phase flips; the waiting thread's mbarrier.try_wait returns (common:817-821). Registers are never used for the data.

Shape D (get into global memory) is shape C followed by the store half of shape B in reverse: TMA writes the tile from shared memory into A's L2.

PATH 3

NVLink multicast (NVLS)

nvshmemi_common_device.cuh:222-325, coll/broadcast.cuh, coll/reduce.cuh

Still thread stores, but to a multicast address: the NVSwitch duplicates each store to every GPU of the team. A broadcast of n bytes to 7 peers then costs the sender n bytes of NVLink traffic instead of 7n. The reverse, multimem.ld_reduce, makes the switch read the same address on all GPUs and return their sum, used for all-reduce.

Where it is used
  1. nvshmemi_mcast_memcpy_threadgroup()common:270-32516/8/4-byte multicast stores; returns the unaligned tail for the caller to send with path 1.
  2. broadcast / fcollect with NVLScoll/broadcast.cuh:494-760, coll/fcollect.cuh
  3. reductions: multimem.ld_reducecoll/reduce.cuh:160-215, choice at :1855-1866

Requirements: NVSwitch with SHARP (Hopper/Blackwell NVLink systems, yes on GB200 NVL72), a team whose GPUs share a multicast object, and NVSHMEM_DISABLE_NVLS not set (src/include/host/env/env_defs.h:42). Point-to-point putmem never uses it.

Memory traffic

#HopWhat happens
1A HBM → A L2Local source read, as path 1.
2A L2 → A L1
3A L1 → registersld.global.v4.b32 (common:229).
4registers → NVSwitchmultimem.st.global.v4.f32 to a multicast address: one write packet leaves A.
5NVSwitch → every memberThe switch copies the packet to each GPU in the multicast group, including A itself, so A's own copy arrives back through NVLink into A's L2.
6each L2 → HBMEach member's L2 is the home for its copy.

multimem.ld_reduce (all-reduce) runs the other way: the SM sends one read request to the switch, the switch reads the same offset from every member's L2, adds the values, and returns one result to the requesting thread's registers. The thread then stores it normally.

PATH 4

Copy engine, started from the host

src/host/comm/putget.cpp:49-188

When the CPU calls nvshmem_putmem or nvshmemx_putmem_on_stream for a mapped peer, NVSHMEM does not launch a kernel: it calls cudaMemcpyAsync from local to peer-mapped address. The CUDA driver hands that to a copy engine, a DMA unit that uses no SM time.

PATH 5

CPU proxy thread + InfiniBand NIC

pt-to-pt/proxy_device.cuh:286-391, src/host/proxy/proxy.cpp, src/modules/transport/ibrc/ibrc.cpp

For a peer not mapped over NVLink, the default device transport is the proxy. The GPU cannot talk to the NIC in this mode, so one thread of the calling group writes a 32-byte request into a ring buffer in host-pinned memory (cudaHostGetDevicePointer, proxy.cpp:104). A CPU thread polls the ring and posts an RDMA write; the NIC then reads the source straight from GPU memory and writes it into the remote GPU's memory.

Call chain, GPU side then CPU side
  1. nvshmemi_transfer_rma_nbi()transfer_device.cuh:266-280PROXY branch: only thread 0 of the group continues.
    1. nvshmemi_proxy_rma_nbi() → transfer_dma()proxy_device.cuh:384, 286-381Reserve 4×8 bytes in the ring (atomic counter), wait if the CPU is behind, write laddr/size/pe words, then the header word (remote offset, op, flag) last so the CPU only sees complete requests.
  2. proxy thread: progress_channels()src/host/proxy/proxy.cpp:1426-1490

      1. nvshmemt_ibrc_rma() → ibv_post_send()ibrc.cpp:1378, 1444RDMA write posted to the NIC; the NIC does the copy.

Properties. Needs no special NIC or driver features, but every operation passes through one CPU thread, which adds latency (the request crosses PCIe to host memory and the CPU must notice it) and limits the message rate for many small puts. The source must be in global memory the NIC has registered: a shared-memory source is not supported (asserts at src/include/internal/host/nvshmem_internal.h:154-158, compiled out in your release build). The blocking nvshmemi_transfer_rma (transfer_device.cuh:152-176) is the same request followed by a proxy quiet.

No separate network buffer: the NIC reads and writes the user's buffers

NVSHMEM does not copy payload into a network staging buffer. The whole symmetric heap is registered with the NIC once, so the NIC's DMA engine reads the source from, and writes the destination into, the application's own buffers in HBM (zero-copy GPUDirect RDMA). On the receiving side there is no receive buffer either: NIC B writes straight into PE B's copy of the symmetric object.

Once per heap allocation: register the memory with the NIC

    1. nvshmemt_ib_common_reg_mem_handle()src/modules/transport/common/transport_ib_common.cpp:418-520Registers GPU memory as a dma-buf memory region when supported (mlx5dv_reg_dmabuf_mr / ibv_reg_dmabuf_mr, :453-497), else ibv_reg_mr_iova / ibv_reg_mr (:508-513). Two consequences. A put's source must be in HBM the NIC can reach (heap or registered buffer), never shared memory or registers. And bulk puts cost no extra HBM traffic on either side: HBM → L2 → NIC on the sender, NIC → L2 → HBM on the receiver. The IB transports cap one work entry at max_op_len bytes and split larger transfers (nvshmem_internal.h:151-153); that splits the request, not the buffer.

PATH 6

IBGDA: the GPU drives the NIC

With IBGDA the NIC's queues and doorbell register are mapped into GPU memory. GPU threads write the WQEs themselves and ring the doorbell, so there is no CPU thread and many GPU threads can post in parallel.

Overview E

When TMA is (and should be) used

NVIDIA's own guidance in the repo (skills/nvshmem-enable-tma/SKILL.md, section 2): "TMA helps only peer-reachable GPU memory paths through the GPU load/store fabric, normally NVLink. Do not recommend it for IB, RoCE, EFA, or another network transport. It is promising for large point-to-point transfers, low communication-thread counts, fused kernels, or tiles already in shared memory. Never promise a speedup without measurement." The reasons below explain why, from how the two paths work; they are not benchmark results.

Good fits

Data already in shared memory

A GEMM or attention kernel's output tile sits in smem. Path 1 would read it into registers and store 16 bytes per thread per instruction; shape A sends the whole tile with one instruction and no registers. This is the only case where you add code (give_smem + proxy fence). Case: tma-smem.cu.

Few threads doing communication

A warp-specialised kernel where one warp, or one thread, owns communication. With ld/st, a single thread keeps only a few stores in flight and cannot fill an NVLink link; one TMA instruction can move up to a full tile regardless of thread count.

Overlap with compute

The _nbi TMA put returns right after issue, and the TMA unit copies while the block's other warps compute. With path 1 the issuing threads are busy until their stores are issued.

Large, aligned transfers

Setup cost (election, mbarrier init, a __syncthreads) is fixed, so it is amortised over large messages. Sizes and addresses must be multiples of 16 anyway.

Poor fits

  • Network peers. TMA only writes to addresses the SM can reach. For IB peers the dispatch never looks at TMA; a registered smem source to a network peer is unsupported (paths 5–6).
  • Global source with a full block of threads. Shape B takes two trips (HBM→smem→peer) through one or two issuing threads, while path 1 with 1024 threads already has many 16-byte stores in flight. Whether B wins here is not obvious; measure.
  • Small or unaligned messages. Scalars (_p, signals) always use a plain store. Anything not 16-byte aligned falls back to path 1 anyway (the TODO at tma_device.cuh:327-330 notes head/tail splitting is not implemented).
  • Kernels that need their shared memory. The recommended 64 KiB per block reduces how many blocks fit on an SM (GB200: 228 KiB per SM), which can slow the compute part more than TMA speeds the copy.
  • Several independent callers in one block. Staged shapes B/D share the one tile and fixed mbarrier slots; for 3.7.x the skill says to "serialize staged TMA calls within a CTA when independent thread- or warp-scoped callers could overlap" (references/gmem-staging.md).
  • More than TMA_MAX_BLOCKS blocks. Default 4096 table entries (env_defs.h:407); blocks beyond that silently use path 1.

What about the copy engine instead?

Pick path 4 when the transfer can happen between kernels and is large: it costs no SM time at all, which neither TMA nor ld/st can match. Pick an in-kernel path (1 or 2) when the data is produced and consumed inside one kernel, when you need fine-grained signalling (put-with-signal, per-tile flags), or when launch overhead per transfer matters. TMA sits between them: in-kernel like path 1, but mostly offloaded from threads like path 4.

Overview G

On Beta, today

  • Inside one node (4 GB200 GPUs): peers are P2P-mapped, so paths 1, 2, 3 and 4 apply.
  • Between nodes of the same rack: GB200 NVL72 puts all 72 GPUs of a rack on one NVLink domain, so multi-node NVLink (MNNVL) would make them P2P too, and TMA would work across nodes. On the nodes tested so far the IMEX channel is broken and runs use NVSHMEM_DISABLE_MNNVL=1 (see dev-guide-ring-fabric-handle-error.md), so other nodes are reached through path 5 (IBRC proxy) instead.
  • Between racks: always network, path 5 in this build.
  • Consequence for tma-smem.cu: running it across two nodes with MNNVL disabled would send a shared-memory source to the proxy, which is unsupported (see the tma-smem walkthrough, step 6).
