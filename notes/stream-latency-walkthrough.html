Host-Issued Copy-Engine Put

How perftest/host/pt-to-pt/stream_latency.cu sends data to a peer GPU from CPU code, where NVSHMEM turns each put into a cudaMemcpyAsync run by the GPU's copy engine, and why putting it on your own CUDA stream is faster than the blocking call. Traced call by call through the NVSHMEM source.

Overview A

What the test shows

In the ring and TMA examples, a GPU kernel calls the put and GPU threads (or the TMA unit) move the bytes. Here the put is called from CPU code, between kernel launches. For a peer GPU whose memory is mapped over NVLink, NVSHMEM then launches no kernel at all: it calls cudaMemcpyAsync from the local buffer to the peer-mapped address, and the CUDA driver gives that copy to a copy engine, a DMA unit on the GPU that works without any SM.

The test compares two ways of making that host call after a kernel. Each iteration is "run a tiny kernel, then send size bytes to the other GPU", and the reported number is the average time per iteration:

  • with _on_stream: nvshmemx_putmem_on_stream(..., strm) puts the copy on your stream, right after the kernel. The CPU only queues work and never waits inside the loop.
  • without _on_stream: the CPU waits for the kernel (cudaStreamSynchronize), then calls the blocking nvshmem_putmem, which queues the copy on an NVSHMEM-internal stream and waits for it too. Each iteration pays two CPU↔GPU round trips.
Overview B

Terms used on this page

PE
Processing element: one process of the job, owning one GPU. This test needs exactly 2.
CUDA stream
A queue of GPU work (kernels, copies, event records). Items on one stream run in order; items on different streams may overlap. The CPU adds items and returns immediately unless it calls a synchronise function.
non-blocking stream
cudaStreamNonBlocking: a stream that does not implicitly wait for the legacy default stream (stream 0).
copy engine (CE)
A DMA unit on the GPU, separate from the SMs, that executes cudaMemcpy*. It reads and writes memory through L2 and NVLink without running threads.
on-stream API
An NVSHMEM host call with a cudaStream_t argument, such as nvshmemx_putmem_on_stream: the operation is ordered after earlier work on that stream, and the CPU does not wait.
blocking (host)
nvshmem_putmem from the CPU returns only when the data has been copied, so the source can be reused.
internal stream
A CUDA stream NVSHMEM creates at init (nvshmemi_state->custreams) for host-issued copies that are not on your stream.
CUDA event
A marker placed on a stream. cudaEventElapsedTime gives the GPU time between two markers.
symmetric heap
Memory from nvshmem_malloc, at the same offset on every PE, so a local address names the peer's copy too.
peer-mapped address
The address in this process where the peer's heap is mapped (over NVLink). A normal copy to it writes the peer GPU's memory.
STEP 1

Start and require exactly two PEs

stream_latency.cu:99-108, perftest/common/utils.cu:324-462

init_wrapper is the shared start-up code of every perftest. Without NVSHMEMTEST_USE_MPI_LAUNCHER or NVSHMEMTEST_USE_UID_BOOTSTRAP it calls plain nvshmem_init(), then select_device(), a barrier, and allocates two 8-byte symmetric scratch values used by device tests (utils.cu:442-460). With NVSHMEMTEST_USE_MPI_LAUNCHER=1 it loads Open MPI, picks the GPU from the node-local MPI rank before init (utils.cu:367-383), then calls nvshmemx_init_attr(NVSHMEMX_INIT_WITH_MPI_COMM, …).

The test then exits unless nvshmem_n_pes() == 2: the peer is always !pe (line 33), i.e. PE 0 talks to PE 1.

One init detail matters for later: NVSHMEM creates its internal streams here. The count is NVSHMEM_MAX_PEER_STREAMS (default 16, src/include/host/env/env_defs.h:197), but on a system with an NVSwitch, which includes GB200, it is forced to 1 unless you set the variable yourself (src/host/init/init.cu:881-885, logged as "NVSHMEM has set MAX_PEER_STREAMS to 1"). Each is created with cudaStreamNonBlocking and the highest stream priority (init.cu:894-897).

STEP 3

Two symmetric buffers and one stream

stream_latency.cu:187-207

Both buffers come from nvshmem_malloc(max_msg_size) and are zeroed with cudaMemset. data_d is the destination: PE 0 writes into PE 1's copy of it. data_d_local is the source on PE 0. Both being in the symmetric heap matters in step 5: NVSHMEM has a faster branch when the local buffer is inside the heap.

cudaStreamCreateWithFlags(&strm, cudaStreamNonBlocking) creates the stream both loops use. With the default -S each PE allocates 256 MiB of heap.

STEP 4

Only PE 0 measures

stream_latency.cu:209-240

PE 0 loops over sizes and repetitions and calls lat(). PE 1 goes straight to nvshmem_barrier_all() and waits there until PE 0 is finished. This is one-sided communication in its plainest form: PE 1's GPU memory is written (or read) the whole time, but PE 1's process and SMs do nothing.

STEP 6

Kernel, wait, blocking host put

stream_latency.cu:45-53

Now the CPU waits for the kernel with cudaStreamSynchronize(strm), because a blocking host put has no stream to order itself after. Then nvshmem_putmem follows the same chain as step 5 as far as nvshmemi_p2p_rma_optimized, but with is_stream = false:

Call chain, on the CPU
  1. nvshmem_putmem()putget.cpp:379-388NO_NBI, NO_ASYNC, stream NOT_A_CUDA_STREAM (0).
    1. … → nvshmemi_p2p_rma_optimized()copy engine:112-142cudaMemcpyAsync(peer_addr, src, size, DeviceToDevice, custrm) on NVSHMEM's internal stream (:128-133), then cudaStreamSynchronize(custrm) (:142): the CPU sleeps until the copy engine is done. Only then does the call return and the loop launch the next kernel.

So per iteration the CPU makes two round trips to the GPU (wait for kernel, wait for copy), and the GPU sits idle while the CPU notices each completion and issues the next step. The difference between the two tables is the price of those round trips.

STEP 7

The get direction (-d 1)

stream_latency.cu:54-73

The PULL branch reverses the order: the get comes first, then the kernel. nvshmemx_getmem_on_stream (putget.cpp:716-726) and nvshmem_getmem (:705-714) go through the same functions. For a get, nvshmemi_prepare_and_post_mapped_rma makes the source the peer-mapped address and the destination data_d_local (:215-221), and the copy is again cudaMemcpyAsync(..., DeviceToDevice, …): on strm for the on-stream loop, on the internal stream followed by cudaStreamSynchronize for the blocking one.

Note the blocking PULL loop has no cudaStreamSynchronize(strm) before the get, unlike the PUSH loop. See Surprises.

STEP 8

Timing and output

stream_latency.cu:36-53, 215-231

Each loop is bracketed by cudaEventRecord(sev, strm) and cudaEventRecord(eev, strm); cudaEventElapsedTime gives milliseconds of GPU time between the two markers on strm. In the blocking loop the copies run on a different stream, but the CPU has already waited for each one before recording eev, so the interval still covers all of them plus the host gaps.

The printed value is ms / iter × 1000: microseconds per iteration, including the kernel, not the copy alone. Two tables are printed by print_basic_table: "Stream_Latency with _on_stream" and "without _on_stream", one row per size. Then both PEs meet at the barrier, free the buffers and call finalize_wrapper.

Overview C

Where the bytes go

Only test_kernel uses an SM, and it touches 8 bytes of data_d_local. That write goes through PE 0's L1 and L2 before the next copy reads the buffer; stream order on strm (step 5) or the explicit synchronise (step 6) make sure the copy sees it.

Overview C2

Below cudaMemcpyAsync: how a copy engine is driven

A copy-engine copy is a short list of commands that the CPU writes into memory. The GPU's front end fetches the list and hands it to a DMA engine. That engine reads and writes by virtual address through the GPU's MMU, using the same page tables in which NVSHMEM mapped the peer's heap, and it signals completion by writing a counter (a semaphore) to memory.

The CUDA driver behind cudaMemcpyAsync is closed source. The chains below therefore come from two places. The NVSHMEM part is traced in this repo. The hardware part is traced in NVIDIA's open kernel driver (open-gpu-kernel-modules, release 615.71.09, commit 61dcc93), whose unified-memory module (UVM) programs the same copy-engine hardware directly for page migration. CUDA's user-space driver uses the same hardware interface (channels, command buffers, work ring, doorbell). Its exact command stream, engine choice and ordering tricks are not public.

GPU hardware④ ⑤ ⑥The front end sees the doorbell, reads the new ring entry and the command buffer, executes the semaphore acquire, and forwards the copy commands to the logical copy engine bound to the channel. The engine splits the transfer over its physical engines and issues reads and writes by virtual address. The MMU sends the source to the local L2 and the destination through the peer page-table entry to NVLink.

Which copy engine

Each logical copy engine reports capabilities to the driver (UvmGpuCopyEngineCaps, kernel-open/common/inc/nv_uvm_types.h:340-383): whether it runs synchronously with the graphics/compute engine (grce), whether it is good at host-memory reads or writes, whether it can do NVLink peer copies (nvlinkP2p), and which physical engines back it (cePceMask). For GPU-to-GPU copies UVM picks the logical engine with the most physical engines, to maximise bandwidth (uvm_channel.c:3010-3017). For host↔GPU copies it prefers engines that are not NVLink peer engines, so it does not take bandwidth from peer traffic (:2988-3006). Which engine CUDA assigns to your stream is not documented.

What stays unknown

  • Pull (get) copies. UVM never lets a copy engine read from a peer. Whether CUDA does it for nvshmemx_getmem_on_stream, or handles it some other way, is not public. NVLink traffic counters (DCGM, or nvidia-smi nvlink) during a -d 1 run would show which direction the link carries data.
  • How CUDA orders a copy after a kernel. It can put a semaphore acquire into the copy channel, as UVM does, or use a copy engine that shares the compute channel (grce). Nsight Systems shows the copy's timing but not the mechanism.
  • Which command set GB200 uses. Hopper's copy engine class is HOPPER_DMA_COPY_A (0xC8B5). Blackwell has BLACKWELL_DMA_COPY_A (0xC9B5) and _B (0xCAB5) (src/common/sdk/nvidia/inc/class/clc9b5.h, clcab5.h). I have not checked which one GB200 reports.
Overview D

What changes if PE 1 is on another node

With the two PEs on different nodes and multi-node NVLink off (your current setup, NVSHMEM_DISABLE_MNNVL=1), get_local_pe_bases()[1] is null and nvshmemi_prepare_and_post_rma skips the copy engine entirely:

Call chains, remote peer
  1. on-stream: nvshmemi_proxy_rma_launcher()proxyputget.cpp:300-311, rma.cu:10-21Launches a 1-thread kernel on strm: nvshmemi_proxy_rma_entrypoint_blocking (src/include/internal/non_abi/nvshmemi_h_to_d_rma_defs.cuh:62-69). It writes a request into the proxy ring and then waits in nvshmemi_transfer_quiet until the CPU proxy thread reports the RDMA write complete. Stream order is kept, but a GPU thread spins for the whole network round trip.
  2. blocking: tcurr->host_ops.rma() → nvshmemt_ibrc_rma()IBRCputget.cpp:258-298, ibrc.cpp:1378-1455The calling CPU thread posts the RDMA write with ibv_post_send, then, because the call is blocking, polls the completion queue until it finishes (check_poll_avail(…, WAIT_ALL), ibrc.cpp:1449-1452). No kernel, no proxy thread.

So the same binary becomes a comparison of "GPU-triggered proxy RDMA" vs "CPU-posted RDMA". That run is the natural next demo for path 5.

Overview F

Surprises in the trace

  • No kernel moves the data. Unlike every device-side example, a host put to a mapped peer is a CUDA memory copy. The SMs are free for other kernels during it.
  • "Blocking" means two different things. putmem_on_stream is blocking in stream order only (the CPU returns at once); nvshmem_putmem blocks the CPU with cudaStreamSynchronize.
  • The latency includes the kernel. Each row is (kernel + copy + gaps) / iterations, not the copy alone.
  • The help text lists a flag that does not exist. -i [Put/Get issue type] is printed and i: is in the getopt string (line 114), but there is no case 'i', so -i falls into default, prints the help and exits.
  • Parameter names are swapped in lat(). It is called with (…, nb, nt, …) = blocks, threads (line 218) but names them ng, nb (line 30), and launches <<<ng, nb>>>. The result is correct (blocks, threads); only the names mislead.
  • The blocking PULL loop is not synchronised with the kernel. Unlike PUSH, it never calls cudaStreamSynchronize(strm): the get on the internal stream can run while the previous test_kernel is still running on strm, and both write data_d_local. With the default 1-cycle kernel the effect is tiny, but with a large -c the "without _on_stream" PULL number hides kernel time. Found by reading lines 64-72; not verified by a run.
  • One internal stream on GB200. Because the node has an NVSwitch, MAX_PEER_STREAMS is forced to 1, so all non-stream host copies to any peer share one internal stream (init.cu:881-885).
  • Only the peer's mapping decides the path. The same two calls become a copy-engine copy, a proxy kernel, or a CPU-posted RDMA depending only on whether PE 1's heap is mapped (step 5, section D).
