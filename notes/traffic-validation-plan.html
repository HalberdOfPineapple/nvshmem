Validation plan

Validating GPU Memory Traffic

A general method for testing, on real hardware, whether a given data flow passes through (or skips) any memory or interconnect component: registers, L1, shared memory, TMA, crossbar, L2, HBM, NVLink, NVSwitch, copy engines, PCIe/C2C, network cards, host memory and CPU. It is applied here to every NVSHMEM path on Beta's GB200 nodes, and works the same way for any memory-semantic fabric.

Overview A

What is being validated: claims, not paths

The traffic model is a list of claims, each of one form:

Flow F (a payload or control stream, with a direction and an issuing engine) passes / skips component C, carrying k · S bytes for a transfer of S bytes, with residency R afterwards (for components that hold state: caches, buffers).

Examples from the model: "an SM put's source read passes the sender's L2, 1·S bytes"; "peer-bound stores skip the sender's L2"; "a copy-engine push uses no SM"; "an NVLS store leaves the sender once and reaches every member"; "an RDMA write arrives in the receiver's L2 and stays there". Validating the model means testing every claim with the same protocol (section C), using whichever kinds of evidence (section B) the component offers (section D). No claim is special; the receiver-L2 one is worked through in section G only as an example.

Overview B

Six kinds of evidence

Each kind can be fooled in its own way; they are useful because they fail independently. A claim is accepted only when at least two kinds agree, and at least one of them is not a hardware counter.

EvidenceQuestion it answersHow, in generalHow it fails
countingHow many bytes crossed C?A hardware counter at C (Nsight Compute, CUPTI, DCGM, NIC or CPU counters), read as a difference between an S-byte run and a 0-byte runwrong counter, wrong scope (per kernel vs device), double counting, profiler side effects
instructionWhich engine issued it, with which instructions?SASS inspection (cuobjdump -sass) and executed-instruction counters (global/shared loads and stores, bulk copies)code present but not executed; runtime fallback paths
stateDid C keep a copy afterwards? (stateful C only)A probe reads the data after the transfer and measures hit rate or traffic at C, compared with a "known present" and a "known absent" controleviction between transfer and probe; the probe itself disturbing C
timingDoes the data behave as if it is at C?Latency signature: a dependent-load chain over the data, compared with controls at each level (L1 hit, L2 hit, HBM, peer)prefetching, clock effects; distinguishes levels only when their latencies differ enough
contentionDoes the flow share C's capacity?Saturate C with an unrelated "contender" workload; if the flow slows down (or the contender does), both use C. If neither changes, the flow does not pass Cshared bottlenecks elsewhere; C not saturable in isolation
knock-outIs C necessary for the flow?Disable or bypass C (environment switch, cache hint, different API) and check that the flow changes path or fails as predictedthe switch changes more than C

Contention and knock-out are the general tools for components that expose no counter at all (the NVSwitch, the copy engine's internals, the proxy's CPU path): they need only a stopwatch and a way to load or remove the component.

Overview C

The test protocol, for any claim

  1. State the claim in the form of section A, with the predicted k and R. Write down what the opposite claim would predict for each piece of evidence before measuring.
  2. Pick evidence from section D: at least two kinds, at least one not a counter.
  3. Build controls on the same GPU where the truth is known: a positive control that certainly uses C (for example a local kernel that writes through L2), and a negative control that certainly does not (for example the same buffer after C is flushed, or a path that cannot reach C).
  4. Isolate the flow. One path, one issuer, fixed source location, alignment and message size, nothing else running. Force the path with NVSHMEM's switches (NVSHMEM_TMA_POLICY, NVSHMEM_DISABLE_P2P, NVSHMEM_DISABLE_NVLS, NVSHMEM_DISABLE_MNNVL) and confirm it by instruction evidence.
  5. Difference run. Repeat with S = 0 and subtract, so barriers, signals, polling and proxy activity cancel.
  6. Sweep. Vary S across the component's capacity (L1, shared memory, L2 size) and a second knob (threads, blocks, concurrent streams). Check that counts scale linearly with S, and that changes of slope occur where the claim predicts, for example at the L2 size.
  7. Calibrate. Use the positive control to measure the counter's factor: sector size, double counting across L2 partitions, link and PCIe packet overhead. Divide it out of every result.
  8. Decide with section I, and record the claim in the model as "measured", with the run's job id.

Overview F

One harness for all tests

A single program (proposed examples/traffic-probe.cu, not written yet) composes every test from three kinds of pieces, so that adding a component or a path means adding a piece, not a program:

PieceChoicesRole in the protocol
Flowissuer (SM ld/st, TMA, NVLS store, host API → copy engine, proxy, IBGDA) × source (global, shared, host) × direction (put, get) × size Sthe claim's F
Instrumentsentinel kernel so a passive GPU can be profiled · consume (read once, chosen cache operator) · chase (dependent-load latency) · flush (per cache level) · local-write (positive control)state, timing and counting evidence
Contenderper component: L2 thrasher, DRAM-bandwidth hog, NVLink stream to the same peer, PCIe host copy, ib_write_bw, CPU hog pinned to the proxy corecontention evidence

Command-line form: traffic-probe --flow put-ldst --src gmem --bytes S --instrument consume --contend l2 --cond arrived|local|flushed. Knock-outs are environment variables and build options, so they need no code.

Overview H

Pitfalls, in general

  • The profiler changes the system. Nsight Compute flushes caches before each kernel by default (use --cache-control none for any state or timing test). It replays kernels once per counter group, which re-sends communication and makes waiting kernels return at once: keep each counter set to a single pass and repeat the job per group. Application replay re-runs only the profiled rank, not its MPI peers, so it does not help.
  • Passive components and GPUs. One-sided transfers leave the receiver without a kernel, and the copy engine, NVSwitch and NIC never run one. Use a sentinel kernel, or sampling over time (Nsight Systems GPU metrics, CUPTI PM sampling, DCGM).
  • Counter scope. Some counters are per SM or per kernel, some device-wide. Linearity in S of a flow the kernel does not issue itself shows that a counter sees external traffic.
  • Counting factors. Sector size, double counting between the two L2 partitions, packet headers on NVLink and PCIe, 4-byte units on NIC counters. Calibrate each with a positive control.
  • Deferred effects. Write-backs, completions and evictions may happen outside the measurement window. Sweep S and window length rather than trusting one run.
  • Silent path changes. NVSHMEM falls back quietly (TMA → ld/st on misalignment, NVLink → network when a peer is unreachable). Confirm the path of every run by instruction evidence or link counters before reading anything else.
  • One rank at a time. Profile through a wrapper that runs the profiler only on the rank of interest.
Overview I

Deciding a claim

ResultDecision
All chosen evidence agrees with the claimAccept; mark the claim "measured" in the model.
All agrees with the oppositeReject; change the model and every result derived from the claim.
Counting agrees, state or timing disagreesThe flow passes C but does not stay (for stateful C): add a residency term.
State, timing and contention agree, counting disagreesThe counter is wrong for this purpose (scope, naming, attribution); keep the behavioural result and fix the counter choice.
Counts scale with S but with an unexpected factorCalibration missing or a hidden flow (for example a partial-sector read-fill, a staging copy); find it before accepting.
Slope changes at an unexpected sizeEffective capacity differs from the specification (partitioning, eviction by other traffic, persistence policy).
