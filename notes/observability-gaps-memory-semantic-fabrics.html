Observability Gaps in Memory-Semantic Scale-Up Networking

What FabricPerf measures, what it structurally cannot, and which of those blind spots are general properties of load/store fabrics rather than quirks of one library. NVSHMEM is the lens because it exposes the fabric's raw primitives (stores, loads, atomics, fences, multicast, bulk-copy engines, network fall-backs) instead of one fixed protocol.

Sources: FabricPerf (Huang & Wu, SIGCOMM '26) · Demystifying NVSHMEM (Ma, Shen et al., arXiv 2606.05951) · NVSHMEM devel @ 7bb2e99 · Markdown version: observability-gaps-memory-semantic-fabrics.md · 2026-09-29

0. The short version

FabricPerf turns "measure the scale-up network" into "profile the NCCL communication kernel": it timestamps five landmarks of NCCL's data-then-fence-then-flag protocol inside the kernel, synchronises GPU clocks with a PTP-style handshake (GPTP), and models fabric traffic as memory traffic so CUPTI counters can be reused. It is a good first step that silently assumes six things true of NCCL ring kernels and false of memory-semantic fabrics in general.

1. What FabricPerf actually measures

Observation unit. One fence-delimited run of stores from one thread block (a "channel") followed by a control-plane write (the "tailer"). The paper concedes these are KB to MB units; the "128-bit MTU" is the store width, not a packet size.

Timestamps. Five per unit, on two GPUs, aligned by GPTP. Probes attach at the SASS level (Neutrino) to three landmarks: the fence, the poll-loop branch, and the first st.

Clock sync. Leader/follower, offset-only, re-run every kernel because inter-kernel jitter is 36 µs (intra-kernel ~100 ns); triangulation error 106 ns average, 365 ns worst; symmetric delay assumed. Physical layer. NCCL's staged buffers are modelled as persistent (should hit L2) versus streaming user buffers. Scope exercised. NCCL 2.28 ring SendRecv / AllGather / ReduceScatter on H100 NVL8 and GB200 NVL16, stores only. Admitted limits. No network layer, no switch, imbalance "regrettably" unattributed.

2. Research gaps

Inclusion criterion: the gap must exist for any memory-semantic fabric. NVSHMEM is evidence and testbed. Excluded as NVSHMEM-specific: the heap allocator, teams and pSync, the dual host/device API, bootstrap, on-stream wrappers.

Gap 1 · There is no canonical "packet" to timestamp

FabricPerf's unit exists because NCCL's protocol has one. The same nvshmem_putmem dispatches at run time to mechanisms with different observable events.

  • No fixed instruction landmarks. LL128 has no fence, TMA has no st, the copy engine has no kernel, multicast has one st for N deliveries.
  • The unit depends on the mechanism. Warp wave, bulk group, 16-byte element, or fan-out set.
  • The same call takes different mechanisms depending on reachability, TMA policy, alignment and build flags.

NCCL's own device API makes the same point. NCCL 2.28, the version FabricPerf profiles, also ships a device API (Hamidouche et al., arXiv 2511.15076) with three modes: LSA (plain loads and stores into peer windows; the application writes its own flags and fences), Multimem (multimem.st via NVLink SHARP), and GIN (one-sided put with a signal for remote and a counter for local completion; ordering comes from the signal "without requiring explicit fence operations", operations are unordered by default). FabricPerf's experiments use only the host-launched collectives, whose Simple protocol is the one realisation of "data, then ordered notification" that has a fence, a plain-store flag and a poll loop at fixed places in a known kernel. The abstract pattern survives across Simple, LL, NVSHMEM put-with-signal and GIN put-with-signal; the probe points do not.

Research question. What is the right observation unit, and where does observation attach when the initiator is not an SM thread? A protocol-free answer: classify every memory instruction by its destination virtual address. Every memory-semantic fabric maps remote memory into known VA windows (NVSHMEM: peer_heap_base_p2p[pe] + offset; NCCL windows and UALink likewise), so "remote, and to which PE" is decidable from the address alone, for stores, TMA, multicast and atomics, inside fused kernels.

Gap 2 · Arrival is not an event; the two-clock problem is a symptom

In a two-sided network the receiver NIC executes something on arrival. In a one-sided memory-semantic network, arrival is a state change in the target's L2 or HBM. No thread on the target runs.

GPTP's costs are structural: it must re-run per kernel (a persistent DeepEP-style kernel has no boundary, and ~1.5 µs/run inter-node drift accumulates); it assumes symmetric delay in the two directions, an asymmetry that in a switched, per-direction-lane fabric under load is itself a quantity to be measured; it uses the fabric under test and stalls the kernel 5 to 10 µs.

Research question. One-sided latency without two clocks, or with sync whose error is bounded independently of asymmetry. Candidates: round-trip decomposition with fetching atomics; timestamp-carrying LL-style stores for relative latency and tails; symmetric-pair probes whose offset cancels; LL/LL128 flags as per-16-byte or per-128-byte arrival ground truth.

Gap 3 · Visibility, ordering and completion differ, and the fence is a sensor

Flow control is also hidden: one-sided puts have no receiver credit (the target buffer always exists); back-pressure happens in store buffers and NVLink credits and surfaces only as store-instruction stalls, visible to instruction sampling but not per destination. NVSHMEM already measures the two ends of this separately in shmem_nbi_issue_rate.cu and shmem_flush_bench.cu.

Research question. Non-perturbing completion observation: which existing side effects (fence latency, store-stall cycles, poll-iteration counts, TMA wait_group latency) carry information about in-flight state, and how well can they be calibrated?

Gap 4 · Reads and atomics are first-class traffic with different physics

Issuer-bound throughput
Bulk get 141 vs put 313 GB/s; scalar g 9 vs p 172 GB/s on H200 NVLink (Demystifying §VII.B). Each thread needs the value before its next dependent op; the metric is outstanding requests per SM, not link bandwidth.
Address-level incast
Signals are atomicAdd_system on one remote 8-byte word (nvshmemi_signal_op); DeepEP uses remote atomics for counts and credits. N senders serialise at one L2 slice. Bytes/s is the wrong metric; per-channel views cannot see it.
Two crossings per read
Request and response use opposite link directions; CUPTI NVLink byte counters cannot separate them; FabricPerf's memory model has no accounting for it.
FabricPerf's position
"ld could be simpler as all timestamps are local" (§7). Locality of timestamps is the easy part.
Research question. Observability for request/response memory-semantic traffic: outstanding-request limits and response ordering per SM, and per-address contention for atomics.

Gap 5 · In-fabric operations: one send, N arrivals, a switch with no clock

Research question. Fan-out skew, reduction latency versus participant count and type, and completion semantics. Needs N-way rather than pairwise sync, or a clock-free design based on the reduction's return value.

Gap 6 · Contention is address-determined; the "channel" is not a link

The L1 is missing from the model, and "bypass" is asserted, not measured. Table 2 marks L1 as bypassed for every collective because network data is external to the core; no L1 counter is reported, and the XBAR metric used is by definition the L1's miss output. Receive-side loads do bypass L1, but for coherence, not locality: L1 is not coherent with remote writes, so loads of a remotely written buffer must be volatile, relaxed/acquire at gpu or system scope, or follow an acquire fence. NVSHMEM's LL receives use ld.volatile.global (nvshmemi_common_device.cuh:1910) and its wait loops read through volatile pointers; NCCL does the same. That rule forces every poll iteration to L2 and sets the poll period behind Gap 2. Local source reads are ordinary cached loads that merely stream once. Stores are write-through, so the L1-side effect that matters is the load/store unit's coalescing of per-thread 16-byte stores into the sector transactions that enter the crossbar and NVLink, where the fabric's real packetisation is decided. TMA and multicast skip L1 via the async proxy for unrelated reasons. The SM-side structures the model omits (outstanding loads, store queue depth, MIO queues) are exactly what makes get issuer-bound and what a fence drains, so Gaps 3 and 4 cannot be expressed in an L2-plus-DRAM model. The unexplained 15% error on ReduceScatter's read flow, the one flow mixing a local and a network operand, is consistent with this omission.

Research question. Attributing traffic to physical paths (L2 slice, port, switch plane) from software-visible addresses via controlled address sweeps correlated with per-link NVML/CUPTI counters, and quantifying compute/communication interference in the shared memory pipeline. The latter is the promise of device-initiated communication, and nothing measures its cost to the communication side.

Gap 7 · Reachability tiers, silent fall-backs and degraded paths

  • The path is decided per peer at init: P2P-mapped, else proxy or IBGDA over a NIC (Demystifying §V.A). On Beta the IMEX channel is broken, so NVSHMEM_DISABLE_MNNVL=1 routes cross-node traffic over InfiniBand although the NVLink rack exists (mem_heap.cpp:133-139).
  • GB200 NVL72 is two-level (4-GPU tray, then switch trays); nothing tells whether a pair traverses one or two switch chips.
  • NVLink is lossless via CRC and replay; FabricPerf discounts loss. Replays and lane degradation appear as unattributed tails; NVML has per-link counters, nothing per kernel or destination.
Research question. Per-operation path attribution and detection of degraded reachability, so tails are attributed to routes rather than averaged into "channel imbalance".

Gaps 8 to 11 · Cost, SIMT aggregation, fusion, zero-copy

8Observation cost and sampling
Latencies 1–10 µs; a store tens of ns; a probe 20 ns (SMEM) or 200 ns (GMEM). Finer units cost proportionally more; online mode is already 9%. Missing: a sampling theory for "one packet in 100" when a packet is 1024 threads, and passive observation reusing existing side effects (%globaltimer reads in wait loops, proxy counters, TMA completion, fence duration).
9Whose timestamp is the packet's?
A "flow" is 32 lanes × hundreds of warps × dozens of blocks; the memory system splits and merges stores; fence scope (cta/gpu/sys) and the TMA async proxy change what is ordered. FabricPerf timestamps once per block from one polling thread, implicitly defining arrival as "last byte visible to one thread". First, median or last is undecided: the load/store analogue of packet latency versus flow completion time.
10The communication layer is inlined
NVSHMEM device APIs are header templates inlined into user kernels; DeepEP calls internal helpers directly; fused GEMM + all-gather kernels issue stores mid-loop; host paths use copy engines with no kernel. There is no fixed kernel to probe. A general tool must classify memory instructions by what they touch (Gap 1) or have memory-system hardware support.
11Zero-copy has no receiver-side event
put writes straight into the destination symmetric buffer (NCCL user-buffer registration likewise). No intermediate buffer, no per-packet receiver copy, only a final flag. Packet rate at the receiver is unobservable in software, and FabricPerf's LLC model (persistent network buffer) does not apply.

3. Where this points

A · Clock-free or asymmetry-aware one-sided latency (gaps 2, 3, 5). Fetching-atomic round-trip decomposition; timestamp-carrying LL-style stores; symmetric-pair probes that cancel offset; fence and TMA wait_group latency as calibrated completion sensors; N-way skew for multicast. Evaluate precision without GPTP and degradation under load asymmetry, which GPTP cannot even detect.

B · Address-based, protocol-agnostic traffic classification (gaps 1, 4, 6, 7, 10). Instrument memory instructions by destination VA window (NVBit, Neutrino, or compiler-inserted). Uniform over stores, loads, atomics, multicast and TMA; works inside fused kernels; per-destination and per-slice statistics correlate with per-link counters to recover path attribution. This is what makes "imbalance, cause unknown" answerable.

C · Interference and completion inside the shared memory pipeline (gaps 3, 6, 8, 9, 11). The research object is the store's life in the memory system, not "the network"; metrics are occupancy, stall attribution and completion distributions, measured through side effects rather than probes.

Not this: re-implementing T1 to T5 on NVSHMEM's put/wait. That inherits every assumption above and adds only a different protocol.
