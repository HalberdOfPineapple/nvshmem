Model

NVSHMEM Memory-Traffic Model

For each NVSHMEM data path: how many bytes each GPU's L2, HBM and links carry per byte of payload, which hardware counter sees each flow, and what cache hit rates to expect. Built in the same style as FabricPerf's model of NCCL, from the NVSHMEM source.

Overview A

Short answer

FabricPerf models NCCL's two-sided transfers, which stage data through a network buffer on the receiver: five flows per byte (read source, send, arrive in the buffer, read the buffer, write the user destination). NVSHMEM's puts and gets are one-sided and write straight into the destination (section "No separate network buffer" in data-movement-paths.html). Only the first three flows exist:

Core model, per byte of payload x (fabric bandwidth)

Sender: read the source once (x from L2, and x from HBM if it is not already in L2). Link: x out, plus packet overhead. Receiver: x written into its L2, and eventually x written back to HBM. That is FabricPerf's "SR(DMA)" column (read 1x, write 2x) for every NVSHMEM put path; gets read 1x and write 1x. The paths differ in who issues the traffic (SM, TMA, copy engine, NIC) and therefore in which counter sees it, and in what comes on top: shared-memory staging for TMA, fan-out in the switch for NVLS, and control traffic for the network paths.

One correction to the paper's model matters for any memory-semantic fabric: stores from an SM or copy engine to a peer bypass the sender's L2, according to NVIDIA's profiler team. The paper models them as cached L2 writes. The byte totals still match, because the paper counts these writes at the L1→crossbar interface, but the "write hit rate 1/2" in its Table 2 is an accounting artefact, not caching (section C).

Measurement (§4.3, pp. 648-649): hit rates are computed byte-wise from crossbar bandwidth (input to L2) versus DRAM bandwidth (output of L2). The crossbar write counter "is measured as the (missed) output of the L1 cache and does not include the external write traffic from the fabric", so flow 3 is added from the application-level receive bandwidth. The reported agreement is 6.86% mean error (Fig. 10). §6.3 finds real L2 hit rates collapse to ~0% at ≥16 channels and ≥350 GB/s on GB200.

Overview C

What changes for NVSHMEM, and one correction

The correction: flow 2 never enters the sender's L2

The paper models flow 2 as cached in the sender's L2 (100% write hit), which is where Table 2's "write hit 1/2" for SR (DMA) comes from: flow 2 hit + flow 3 miss. NVIDIA's profiler team states the opposite about the path itself:

"SM to NVLINK or copy engine to NVLINK will bypass L2 so nvl{rx,tx}__bytes_packet_{request,response}_* can be used to provide slightly more information." And: "There are not good metrics from the sender side to understand traffic over nvlink." NVIDIA forum

NVIDIA developer forum, "NCU L2 metric understanding" (thread 361731), NVIDIA staff reply.

This is consistent with the paper's own numbers: their crossbar write counter is L1's output, which includes peer-bound stores before they are routed to NVLink, and flow 2 never reaches DRAM, so byte-wise "crossbar in − DRAM out" makes it look like a hit. The total bytes are right; the interpretation is not. It matters for three reasons:

  • A sender-side L2 counter (lts__*) will not show flow 2. Only the L1→crossbar counter and the NVLink transmit counter do.
  • Flow 2 cannot evict anything from the sender's L2, so it does not compete with the source read (flow 1) for cache space.
  • For copy-engine traffic there is no L1→crossbar counter at all (no SM involved), so flow 2 is visible only as NVLink transmit bytes.

Everything else in this page keeps FabricPerf's convention so the numbers can be compared: memBw summed over both GPUs, flow 2 counted where it leaves the SM.

Where each row comes from

Staged TMA (2B) goes HBM → L2 → shared memory → NVLink; the extra hop is inside the SM's SRAM, so it adds no L2 or HBM traffic but uses shared-memory bandwidth twice.
  • 3: multimem.st / multimem.ld_reduce in collectives (common:222-325, coll/reduce.cuh:160-215) source; one packet out, N copies from the switch hardware behaviour, public NVLS descriptions.
  • 4: cudaMemcpyAsync (putget.cpp:49-148) source; the command-buffer size is estimated from the open driver's method sequence (uvm_turing_ce.c:248-309, ~10 32-bit methods plus a semaphore release) inference.
  • 5, 6: the heap is registered with the NIC, so there is no staging copy (transport_ib_common.cpp:418-520) source. Request size 32 B (PROXY_DMA_REQ_BYTES, transport_constants.h:40) source.

Control traffic grows with time, not bytes

Everything above scales with x. Polling does not: a thread in nvshmem_wait_until (volatile loads, wait_until_apis.cuh:37-48), an IBGDA thread polling its completion queue, or the proxy thread polling its ring generate L2 read requests for as long as they wait. On the receiver that is the only SM-side traffic a one-sided transfer causes, and it can outnumber payload sectors for small messages inference. A model of "communication traffic" therefore needs a time term: polls/s × sectors per poll.

For NVLS, "Write" counts one send plus N arrivals. For gets, the response lands in registers (SM get) or shared memory (2C), not in memory; the only memory write is the requester's local store (SM get) or the copy engine's local write (pull).

The headline for any one-sided, zero-copy fabric API: one read and two writes per byte, instead of two and three, i.e. 40% less memory traffic than a two-sided, buffered exchange for plain transfers. It holds only for transfers that need no receiver processing; a reduction must still read and write at the receiver (section H).

Overview G

Cache behaviour: two regimes, not one

The paper assumes user buffers are streaming (0% hit) and network buffers are reused (100%). NVSHMEM has no network buffer, so its hit rates depend on how the transfer sits in the application:

Standalone transfer (benchmarks, paper's case)

Source cold: flow 1 hit 0%, HBM read x. Destination written into B's L2 and written back when evicted: B HBM write x. Consumer later reads from HBM. Matches Table 2.

Fused producer → put → consumer (typical NVSHMEM use)

The source was just written by the same kernel, so flow 1 hits in A's L2 (HBM read ≈ 0) if the working set fits. The consumer on B reads soon after arrival, so its reads hit B's L2 and B's HBM write-back may be deferred. Communication traffic then approaches: A L2 read x, link x, B L2 write x, with little HBM traffic.

Which regime applies is set by working-set size against L2 capacity (cudaDevAttrL2CacheSize), and by the time between arrival and consumption against the time other traffic takes to evict the lines. The paper's §6.3 result, hit rates collapsing at high bandwidth because buffers are evicted, is the second condition failing. Their fix (PTX .L2::evict_first / evict_last hints) applies to SM-issued accesses only; copy-engine and NIC traffic carry no per-access hint.

L1. The paper's "network data should bypass L1" reads as a hit-rate rule. In NVSHMEM the L1 question arises only for SM-issued accesses. Flow 1 may allocate in L1 but is read once. Flow 2 is a write-through store. Flow 3 never touches any L1 (it arrives at L2). Reuse by the consumer is the application's business. The only place L1 must be bypassed is polling, for correctness (volatile / acquire loads). See data-movement-paths.html, "Memory parts".

Two L2 partitions. GH100 and GB100 split L2 into two partitions joined by an internal fabric ("ltcfabric"); an access homed in the far partition is seen by both. This can inflate raw lts__ totals relative to the model, and the model has no term for it NVIDIA forum size of the effect unknown.

Overview H

Composing collectives

NVSHMEM collectives are built from these paths, so their traffic is a sum of rows from section E. Two examples show the rule and where one-sided loses its advantage.

Reduction step (any path)put, then receiver reads its input and the arrival, writes the sumas a putarrival write m, then read 2m, write m: FabricPerf's flows 4–5 return

This is how the paper's "DMA-style only applies to SendRecv and AlltoAll" shows up in a one-sided library: zero-copy removes the receiver's copy, not its computation. NVLS ld_reduce is the exception that moves the reduction into the switch (section E, row 3). The per-algorithm counts depend on which algorithm NVSHMEM picks per size and team, which is not traced here.

Overview I

Checking the model on Beta

Not yet run. Plan, per path, compare measured counters with section E for a sweep of sizes:

  • Path 1 / 2: perftest/device/pt-to-pt/shmem_put_bw with NVSHMEM_TMA_POLICY=DISABLE vs ENABLE (the --use_smem default is 1). On the sender kernel, expect l1tex__m_l1tex2xbar_write_bytes ≈ x, lts__t_sectors_srcnode_gpc_op_read × 32 ≈ x, and lts__*_op_write near 0 for peer stores (the correction in section C).
  • Path 4: perftest/host/pt-to-pt/stream_latency. Expect L2 reads under srcnode_hub on the sender and no SM counters.
  • Path 5: the same put test across two nodes (NVSHMEM_DISABLE_MNNVL=1). Expect NVLink ≈ 0 and PCIe ≈ hx.
  • Receiver side: in a one-sided transfer the receiver runs no kernel, so kernel-scoped profiling (ncu, CUPTI per-kernel) has nothing to attach to. That is gap 11 in observability-gaps-memory-semantic-fabrics.md. Use device-wide sampling instead: Nsight Systems GPU metrics, CUPTI range or PM sampling across the run, or DCGM profiling fields for NVLink and DRAM. The paper notes CUPTI inter-node hangs for LLC metrics on NVL16 (p. 652, footnote 3).

Measuring h (link overhead) is a by-product: nvltx bytes ÷ payload bytes for large puts.

Overview J

Limits and open points

  • Provenance. Instruction sequences, buffers and registration are from the NVSHMEM source. Hardware routing (L2 bypass for peer stores, hub attribution, ltcfabric) is from NVIDIA forum replies and public descriptions, not a specification. Multiples involving TMA counters, NVLS replication and copy-engine command size are inferences.
  • Partial-sector writes. Signals and scalar puts write 8 bytes into a 32-byte sector. Whether L2 must read-fill such a sector from HBM is not modelled.
  • Pulls. Which GPU's copy engine executes a pull is unknown (stream-latency walkthrough, C2); the byte totals do not depend on it, the per-GPU attribution does.
  • General lesson for memory-semantic fabrics. For zero-copy, one-sided transfers the traffic model is fixed by three flows. What varies, and what a model or a monitor must capture, is who issues them (visible only through different counters), control traffic that scales with waiting time, and cache residency, which depends on the application rather than the protocol.
