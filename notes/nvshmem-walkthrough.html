Overview A

Code map

NVSHMEM ships as two libraries plus runtime plugins. The split explains most of the call chains below: anything a kernel calls is compiled into your binary, while initialization, memory mapping and networking live in a shared library that loads its bootstrap and network backends with dlopen.

Overview B

Three ideas that explain the rest

PEs and the symmetric heap

Each process is a PE (processing element) that owns one GPU. nvshmem_malloc is collective: every PE calls it with the same size, in the same order, so the buffer lands at the same offset inside every PE's heap. The heaps themselves start at different virtual addresses on different PEs. To reach a peer, NVSHMEM keeps a table of peer base addresses and adds the offset.

Two ways to reach a peer

Load/store (P2P)

The peer's heap is mapped into your GPU's address space. A put is an ordinary store instruction; the hardware carries it over NVLink. No CPU involvement at all.

Network (proxy or IBGDA)

With the proxy, the GPU writes a small request into a ring buffer in pinned host memory, and a CPU thread posts it to InfiniBand. With IBGDA (not in your build), the GPU writes the IB work request itself.

State flows from host to device

The host library builds one struct, nvshmemi_device_host_state_t (src/include/non_abi/device_host/nvshmemi_runtime_types.h:419). It holds mype, npes, heap_base, the two peer-base tables, job_connectivity and the proxy ring pointers. nvshmemi_update_device_state() (src/host/init/init.cu:216) copies it with cudaMemcpy into the __constant__ nvshmemi_device_state_d symbol that every device function reads.

Initialization happens in two stages here

This example calls nvshmem_init() before cudaSetDevice(), so no CUDA context exists yet and NVSHMEM cannot know which GPU to use. It stops after the bootstrap. The heavy part (heap, transports, proxy thread, teams) runs later, inside the first call that needs it: nvshmem_malloc() in step 3. If a program selects its GPU first, all of that runs inside nvshmem_init() instead. NVSHMEM_BOOTSTRAP_TWO_STAGE forces the deferred behaviour.

STEP 2

Pick the GPU

dev-guide-ring.cu:24-26

nvshmem_team_my_pe(NVSHMEMX_TEAM_NODE) works even though init is half done, because for the NODE team it does not consult a team object at all. It returns the value the bootstrap computed from the host-hash allgather.

On a Beta node with four GPUs, PEs get mype_node 0–3, so cudaSetDevice(mype_node) gives each PE its own GPU. cudaStreamCreate then creates the primary CUDA context that step 3 needs.

STEP 3

This call does two jobs. Its first line finishes the initialization deferred in step 1. Then it allocates 4 bytes from the symmetric heap on every PE and ends with a barrier so nobody writes before everyone has allocated.

3c · How peers' heaps get mapped

This is what fills the peer_heap_base_p2p table from the core ideas. With the VMM heap (the default on these GPUs):

  • Reserve. Each PE reserves one large virtual range holding a slot per P2P-reachable PE (cuMemAddressReserve, mem_heap.cpp:971). Slot 0 is its own heap.
  • Plan. plan_vmm_peer_bases() (heap_registration.cpp:672) gives each load/store-reachable peer the next slot and records it in peer_heap_base_p2p.
  • Export. export_p2p_memory() (heap_registration.cpp:427) turns each physical chunk into a shareable handle. On an NVLink-fabric system such as GB200 NVL72 this is a CU_MEM_HANDLE_TYPE_FABRIC handle; otherwise a POSIX file descriptor sent over a Unix socket. The choice is made in mem_transport.cpp:384.
  • Import and map. map_p2p_memory() (heap_registration.cpp:211-349) imports each peer's handle and cuMemMaps it at the same offset inside that peer's slot.
  • Register for the network. register_remote_chunk() (heap_registration.cpp:473) calls the IB transport's get_mem_handle (ibv_reg_dmabuf_mr or ibv_reg_mr) and allgathers the resulting rkeys.

The proxy, from the GPU's request to the wire

At init, nvshmemi_proxy_create_channels() (proxy.cpp:272) allocates the ring and its counters in pinned host memory with cudaMallocHost, so the GPU can write them and the CPU can poll them. The GPU writes each entry's flag byte last; the CPU reads an entry only after the flag matches the current lap around the ring.

Overview C

What happens on Beta (GB200 NVL72)

Your build (build/CMakeCache.txt) has NVSHMEM_IBGDA_SUPPORT=OFF, UCX and libfabric off, GDRCopy on, and installs one remote transport, ibrc. With that build, step 4 takes one of two paths.

All PEs in one rack

Up to 18 nodes × 4 GPUs share one NVLink domain. The P2P transport's can_reach_peer grants load/store access across nodes when the peer is on the NVLink fabric (src/host/transport/p2p/p2p.cpp:56-61), heap chunks are shared with fabric handles, and nvshmem_int_p is a single store even to a GPU on another node. The barrier signals are stores too, with no quiet.

PEs span racks

Peers in other racks have null peer_heap_base_p2p entries, so puts to them go through the proxy thread and ibrc. Because the job is no longer load/store-only, every barrier signal becomes a network atomic and the barrier kernel starts with a quiet.

Known problem on node b4-31-s1-dgx-04-c12 (seen 2026-09-25)

On this node, creating fabric-handle memory (cuMemCreate with CU_MEM_HANDLE_TYPE_FABRIC) fails with CUDA_ERROR_NOT_PERMITTED. The IMEX channel device node has the wrong major number, which only the admins can fix. NVSHMEM picks fabric handles automatically on GB200, so nvshmem_malloc fails there. For single-node runs, set NVSHMEM_CUMEM_HANDLE_TYPE=FILE_DESCRIPTOR. Cross-node NVLink runs, as described in the "All PEs in one rack" case above, need the admin fix first. To check whether it is still broken, compare grep imex /proc/devices with ls -l /dev/nvidia-caps-imex-channels/.

To watch these decisions at run time, set NVSHMEM_DEBUG=INFO; lines such as nvshmemi_common_init failed, continuing (step 1) and the P2P transport's per-peer reachability messages come from the INFO(...) calls cited above. NVSHMEM_INFO=true prints every environment setting in effect. To get GPU-initiated InfiniBand instead of the proxy, rebuild with -DNVSHMEM_IBGDA_SUPPORT=ON and run with NVSHMEM_IB_ENABLE_IBGDA=1.

Overview D

Surprises in the trace

These are details that differ from what the API docs or intuition suggest.

  • Init can be lazy. In this example most of the work in "init" happens in nvshmem_malloc, because the GPU is chosen after nvshmem_init(). Timing nvshmem_init() alone is misleading.
  • Heaps do not share a base address. Symmetry is by offset. Two tables do the translation: peer_heap_base_p2p (where a peer's heap is mapped in my address space) and peer_heap_base_remote (the peer's own base, used for IB).
  • The P2P put is a plain store, not a volatile one (nvshmemi_common_device.cuh:1428). Ordering comes from quiet, fence and the barrier.
  • The on-stream barrier skips quiet in all-NVLink jobs (barrier.cu:20-22). In this example, the stores from simple_shift are ordered before the barrier by the kernel boundary on the same stream. That is our reading of the code, not something it states.
  • A static heap cannot grow. With NVSHMEM_DISABLE_CUDA_VMM=1, running out of heap makes nvshmem_malloc return NULL without its final barrier (mem_heap.cpp:2303-2305). Size the heap with NVSHMEM_SYMMETRIC_SIZE in that mode.
  • Two copies of the device state exist. libnvshmem_host.so links its own copy of the device library for the kernels it launches (barriers, collectives), and your binary has another. nvshmemi_update_device_state() writes both through registered callbacks.
